# Specification Amendment A-002: Redefining Identity Level I3 as Site-Keyed Noise (FPP) and Stating Container Limitations

**Amendment ID:** A-002  
**Date:** 2026-10-24  
**Status:** PROPOSED (Pending Owner Approval)  
**Affects:** docs/spec/ (Part 5.1, Part 5.3, Part 6.1)  
**Architectural Origin:** Decision D-005, D-012, SPIKE-002 resolution, Phase 2b empirical testing (`tests/axes/probe_container_canvas.py`)

---

## 1. Summary of Architectural Realignment

The Master Specification (Part 5.3) originally defined Identity level **I3 (Cell-seeded)** as generating noise per Cell and per site using an internal secret key:
> $\text{Noise} = \text{HMAC}(K_{\text{cell}}, \text{registrable\_domain}(D) \parallel \text{api\_name})$  
> *Result: stable inside a Cell and site... unrelated across Cells.*  
> *Spec directive: "Research first: check whether the engine's newer fingerprinting protection already provides seeded randomization before building your own."*

In Phase 2b, empirical investigation on Firefox ESR 153.5.1esr tested Mozilla's native `privacy.fingerprintingProtection` (FPP) subsystem (`EfficientCanvasRandomization`, target 76).

### Empirical Findings:
1. **Engine Support for Site-Keyed Noise:** FPP natively implements deterministic, origin-isolated canvas noise derived at the encoder level (`nsRFPService::RandomizePixels`), satisfying the goal of stable within-origin rendering without breaking graphics editors.
2. **The Container Canvas Limitation:** In Gecko, the random noise key is derived strictly from the site principal / eTLD+1 origin, **without incorporating the container identifier (`userContextId`)**.
3. **Empirical Proof:** As verified by `tests/axes/probe_container_canvas.py`, opening the same origin in Container 1 (`userContextId: 1`) and Container 2 (`userContextId: 2`) within the same Gecko instance produces the **exact same canvas noise** (`dataUrlHash` identical).

Amendment A-002 redefines I3 to reflect this empirical reality, honestly records the limitation of Multi-Account Containers regarding canvas noise, and binds cross-Cell canvas isolation to process-level separation.

## 2. Proposed Amendments by Spec Part

### 2.1 Amendment to Part 5.1: The Identity Axis Table

**Current Text:**
| **I: Identity** | What can a site learn about this device? | I1 Native, I2 Uniform, I3 Cell-seeded, I4 Minimal-API |

**Amended Text:**
| **I: Identity** | What can a site learn about this device? | I1 Native, I2 Uniform, I3 Site-keyed noise (FPP), I4 Minimal-API |

---

### 2.2 Amendment to Part 5.3: Axis I (Identity Levels)

**Current Text Concept (Part 5.3):**
> I3 is "Cell-seeded noise per Cell and site" derived via $HMAC(K_{\text{cell}}, ...)$.

**Amended Text:**
> **Level I3: Site-Keyed Noise (FPP)**
> - **Mechanism:** Backed natively by Gecko's `privacy.fingerprintingProtection` (FPP) with target `EfficientCanvasRandomization` (target 76).
> - **Behavior:** The browser injects deterministic pseudo-random perturbation into canvas and graphic readbacks. The perturbation salt is stable for origin $A$, but differs for origin $B$.
> - **Container Limitation (Honest Boundary):** Within a single Gecko instance, `userContextId` (Multi-Account Containers) isolates cookies, localStorage, IndexedDB, and cache partitions, but **does not partition the canvas randomization key**. Two Cells running inside the same process instance visiting tracking domain $T$ will receive the **same canvas perturbation**.
> - **Cross-Cell Canvas Isolation:** To achieve complete canvas isolation across two distinct Cells (such that domain $T$ cannot link them via canvas noise), the Cells must run in **separate process instances** (e.g. Standard Tier instance vs Guarded Tier instance vs Research Tier instance), as established in Amendment A-001.
> - **Rule R2 Restriction:** I3 is **strictly refused in Tor mode (N2/N3)**. In Tor mode, site-keyed noise creates an outlier fingerprint that splits the Tor crowd; Tor mode strictly mandates I2 (Uniform Tor Browser profile).

---

### 2.3 Amendment to Part 6.1: Cells and Container Boundaries

**Amended Text:**
> - Cells mapped to the same process tier share an underlying browser engine and graphics stack.
> - Client-side state (cookies, web storage, cache, ServiceWorkers) is strictly partitioned per Cell via `userContextId`.
> - However, Cells sharing a single process instance share the same site-keyed canvas noise seeds under I3. When threat modeling requires preventing cross-Cell tracking via canvas fingerprinting, the user must assign the Cells to separate process tiers (e.g., Anchored Banking in Tier 2 Guarded vs General Surfing in Tier 1 Standard).

---

## 3. Impact Assessment

* **Implementation Complexity:** Avoids complex, invasive C++ engine patches to rewire Gecko's internal `CookieJarSettings` and `nsRFPService` to hash `userContextId` into every canvas extraction pipeline.
* **Honesty & Verification:** Replaces an unverified theoretical claim ("Cell-seeded HMAC") with an empirically verified browser primitive, clearly communicating what containers can and cannot isolate.
* **Architecture Alignment:** Fully supports and justifies the 4-instance Process-Tiered architecture of A-001.
